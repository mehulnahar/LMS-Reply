<task type="auto">
  <name>Task 1: Create mockupDecision.js decision matrix module</name>
  <files>src/utils/mockupDecision.js</files>
  <action>
Create `src/utils/mockupDecision.js` as a CommonJS module (`'use strict'`, `require/module.exports`).

Implement `evaluateMockupDecision(job, email)` — a pure sync function with no DB or Express coupling.

**Decision matrix logic (strict priority order):**

1. **Budget gate:** Parse `job.amount` as float. If amount > 0 AND amount < 1000, return `{ shouldBuild: false, projectType: 'low_budget', whatToMockup: null, alternativeSuggestion: 'Relevant case study instead' }`. Treat null/empty/0 as "no budget info" (do NOT block).

2. **Text assembly:** Concatenate `job.job_heading`, `job.job_description_raw || job.job_description`, `job.category`, `job.sub_category` — filter nulls, join with space.

3. **NO keyword check first (more restrictive):** Define regex patterns for:
   - SEO/marketing: `/\b(seo|search\s?engine\s?optim|marketing\s?campaign|ppc|adwords|social\s?media\s?management)\b/i`
   - DevOps/infra: `/\b(devops|ci\/?cd|docker|kubernetes|infrastructure|server\s?setup|deployment)\b/i`
   - Content writing: `/\b(content\s?writ|blog\s?post|copywriting|article|ghostwriting)\b/i`
   - Data entry/admin: `/\b(data\s?entry|bookkeeping|virtual\s?assistant|transcription)\b/i`
   - Backend-only: `/\b(api\s?only|backend\s?only|microservice|cron\s?job|script)\b/i`

   BUT: If a NO keyword matches, ALSO check YES keywords. If BOTH match, apply this rule:
   - **Service-type NO keywords** (SEO, content writing, data entry) take PRIORITY even if YES keywords co-occur. "SEO optimization for e-commerce site" → NO, because the job is fundamentally non-visual service work. The e-commerce keyword refers to the client's existing site, not what we'd build.
   - **Infrastructure-type NO keywords** (DevOps, backend) yield to YES keywords that indicate a genuine visual component. "DevOps pipeline with monitoring dashboard" → YES, because the dashboard IS a buildable UI component.

   Implementation: Split NO categories into `serviceNoCategories` (seo, content, data_entry) and `infraNoCategories` (devops, backend). Service NO + any YES = still NO. Infra NO + any YES = YES.

   NOTE: The cold/engagement gate (MOCKUP-01 requirement for follow_up_count-based timing) is intentionally NOT in the decision matrix — it is handled in Plan 02's pipeline integration via the follow_up_count check in replies.js, because it requires runtime state (follow_up_count) that the pure function doesn't have access to.

4. **YES keyword check:** Define regex patterns for:
   - Web app/SaaS: `/\b(web\s?app|saas|platform|portal|crm|erp)\b/i`
   - Landing page/website: `/\b(landing\s?page|website|web\s?site|homepage|marketing\s?site)\b/i`
   - E-commerce: `/\b(e-?commerce|shopify|woo\s?commerce|online\s?store|storefront|product\s?page)\b/i`
   - Mobile app: `/\b(mobile\s?app|ios\s?app|android\s?app|react\s?native|flutter)\b/i`
   - Dashboard: `/\b(dashboard|admin\s?panel|analytics|data\s?viz|chart|reporting\s?tool)\b/i`
   - AI chatbot: `/\b(chatbot|chat\s?interface|conversational\s?ui|ai\s?assistant)\b/i`
   - Automation tool: `/\b(automation\s?tool|workflow\s?builder|pipeline\s?ui|status\s?dashboard)\b/i`
   - Generic UI: `/\b(ui|ux|design|redesign|frontend|front-?end|user\s?interface|prototype)\b/i`

5. **Default (no match):** Return `{ shouldBuild: false, projectType: 'unknown', whatToMockup: null, alternativeSuggestion: 'Unclear project type -- focus on insight in the reply' }`.

**Return shape:** `{ shouldBuild: boolean, projectType: string, whatToMockup: string|null, alternativeSuggestion: string|null }`

- `projectType` is a category key (e.g., 'web_app', 'landing_page', 'seo', 'devops', 'low_budget', 'unknown')
- `whatToMockup` is an inferred short description for YES results (e.g., "SaaS dashboard", "e-commerce storefront") — derive from matched keyword + job_heading
- `alternativeSuggestion` provides a concrete alternative for NO results:
  - seo: 'Quick keyword/competitor analysis'
  - devops: 'Architecture diagram'
  - content: 'Sample content calendar'
  - backend: 'Code audit with 3 findings'
  - data_entry: 'Workflow optimization proposal'
  - low_budget: 'Relevant case study instead'
  - unknown: 'Unclear project type -- focus on insight in the reply'

**Helper functions (internal, not exported):**
- `detectNoCategory(pattern)` — maps NO regex to category key
- `detectYesCategory(pattern)` — maps YES regex to category key
- `inferWhatToMockup(text, categoryKey, jobHeading)` — creates a short description

**Null safety:** If `job` is null/undefined, treat all fields as empty strings. If `email` is null/undefined, ignore it (email is not currently used in decision matrix but is passed for future extension).

Export: `module.exports = { evaluateMockupDecision };`

<task type="auto">
  <name>Task 2: Add extractColorsFromHtml to prefetch.js analyzeUrl</name>
  <files>src/utils/prefetch.js</files>
  <action>
Add an `extractColorsFromHtml($)` function to `src/utils/prefetch.js` (internal helper, not exported). This function receives a Cheerio `$` instance and returns an array of color strings (hex + rgb).

**Color extraction logic:**
1. Scan all elements with `[style]` attribute for hex (`#XXX` or `#XXXXXX`) and rgb/rgba patterns
2. Scan all `<style>` tag contents for the same patterns
3. Check `<meta name="theme-color">` content attribute
4. Filter out common non-brand colors: `#000`, `#000000`, `#fff`, `#ffffff`, `#333`, `#333333`, `#666`, `#666666`, `#999`, `#999999`, `#ccc`, `#cccccc` (case-insensitive)
5. Cap at 10 colors maximum
6. Return `[]` if no colors found (not null, not undefined)

**Regex patterns:**
- HEX: `/#(?:[0-9a-fA-F]{3}){1,2}\b/g`
- RGB/RGBA: `/rgba?\(\s*\d{1,3}\s*,\s*\d{1,3}\s*,\s*\d{1,3}(?:\s*,\s*[\d.]+)?\s*\)/g`

**Integration into analyzeUrl():**
After the existing Cheerio-based analysis (after tech stack detection, after findings), add:
```javascript
result.colors = extractColorsFromHtml($);
```

Also update the `result` object initialization to include `colors: []` as a default (alongside url, status, title, etc.).

Do NOT modify any existing behavior of `analyzeUrl()` — only ADD the `colors` field. The existing `techStack`, `findings`, `bestFindingForReply` must remain untouched.

Do NOT export `extractColorsFromHtml` — it is an internal helper only.
